# we-grid sample applications

Three self-contained Angular applications that use `we-grid-angular` the way a real product would.
They live in this workspace and are registered in `angular.json`, so they build and serve with the
Angular CLI like any other project here.

Unlike `projects/playground` (a feature-by-feature scratchpad for developing the library), each app
here is a small, believable screen: real column sets, a mock backend, and its own minimal CSS — no
Bootstrap, Material or any other CSS framework.

| App | Domain | What it is there to show |
|---|---|---|
| `banking` | Account activity + loan portfolio | Currency columns with mixed per-row currencies, negative amounts coloured through a custom cell template, a pinned account column, a date-range (`between`) filter, backend-supplied summary totals, master-detail row expansion |
| `retail-market` | Products and stock | Grouping with per-group subtotals, a boolean column and its boolean filter, `rowClass` row highlighting, multi-row selection with a bulk action bar, a density switch |
| `ecommerce-dashboard` | Order operations | **The server-side reference example**: paging + sorting + filtering against a mock backend, KPI cards computed over the filtered set, a status badge column driven by `displayValue`, layout persistence through a custom `WeGridLayoutStore` |

## Running them

The apps resolve `we-grid-angular` through the workspace `tsconfig.json` path alias, which points
at `dist/we-grid` — so build the library once first:

```bash
npm install
npm run build:lib             # required before the first app build/serve

npm run start:banking             # http://localhost:4200
npm run start:retail
npm run start:ecommerce
```

Production builds:

```bash
npx ng build banking
npx ng build retail-market
npx ng build ecommerce-dashboard
```

## Data

Datasets live under `<app>/src/assets/data/` and are generated by
[`tools/generate-data.mjs`](tools/generate-data.mjs) with a seeded PRNG, so regenerating produces
the same files:

```bash
node SampleUsageProjects/tools/generate-data.mjs
```

| File | Rows | Format |
|---|---|---|
| `banking/src/assets/data/transactions.json` | 420 | JSON (each row carries its own fee breakdown for the master-detail view) |
| `banking/src/assets/data/loans.json` | 160 | JSON |
| `retail-market/src/assets/data/products.json` | 400 | JSON |
| `ecommerce-dashboard/src/assets/data/orders.xml` | 500 | XML — parsed with `DOMParser` in the mock service |
| `ecommerce-dashboard/src/assets/data/orders.json` | 500 | JSON — the same rows, kept for reference/diffing |

**Everything is fictional.** Person names, company names, carriers and cities are invented; account
numbers are deliberately unusable placeholders in the shape `TR00 0000 …`. No real customer, bank
or company data appears anywhere in this folder.

## Mock backends

Every app has a service that loads its data file once, caches it, and then answers queries the way a
server would — filter, sort, page, `{ items, totalCount, totalPages }`, plus a `delay(300)` to make
the loading states visible:

- `banking/src/app/services/banking-api.service.ts`
- `retail-market/src/app/services/retail-api.service.ts`
- `ecommerce-dashboard/src/app/services/order-api.service.ts`

They share `mock-query.util.ts` (copied into each app so every sample stands alone), which mirrors
the filter semantics the grid applies client-side — `contains`/`startsWith`/`equals` for text,
`eq`/`gt`/`lt`/`between` for numbers, day-granular comparison for dates, tri-state booleans.

In a real application none of that code exists: the filter list becomes a `WHERE` clause, the sort
becomes `ORDER BY`, and the page becomes `OFFSET/FETCH`.

## Notes worth knowing before copying this code

- **The grid never pages by itself.** It renders every row in `data`; `page`/`pageSize` only drive
  the pager UI and the events. The banking loan grid deliberately shows the other side of that: the
  whole list is handed over and there is no pager at all.
- **Grouping, and client-side filtering/sorting, operate on the loaded rows.** With server-side
  paging that means the current page — the grid itself warns about this when it applies.
- **`rowClass` classes must be defined in a global stylesheet.** They land on the grid's own `<tr>`,
  inside the library component, where a component-scoped rule from your page cannot reach. See
  `retail-market/src/styles.scss`.
- **Custom cell templates are the opposite case**: they are compiled in your component, so your
  component-scoped styles do apply to them.
- **`density` is a public field, not an `@Input`.** Driving it from the host app (as
  `retail-market` does) means setting it on the component instance; since the grid is `OnPush`, the
  change only renders when something else marks its view dirty. The sample hands `data` a fresh
  array reference for exactly that reason. Density set this way is also not written to the saved
  layout — only the grid's own header menu persists it.
- **`displayValue` changes what text filtering searches, not what the backend receives.** The grid
  still reports the filter under the raw field (`statusCode`); mapping the typed label onto a code
  is the backend's job — `order-api.service.ts` shows that translation step.
